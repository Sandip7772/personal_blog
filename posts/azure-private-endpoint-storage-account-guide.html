Azure Private Endpoint step by step: set it up and prove it works

A Storage Account with a public endpoint is one misconfigured firewall rule away from being reachable by anyone. A Private Endpoint removes that exposure by giving the account a private IP address inside your own virtual network, so traffic never crosses the public internet.

This post walks through the full exercise I use to test it: create a locked-down Storage Account, attach a Private Endpoint, and then prove it works from a test VM in the same VNet. The proof matters as much as the setup. A Private Endpoint that is created but not tested is only an assumption.

I use a Storage Account (blob) as the example, but the same pattern applies to anything that supports Private Link, including Key Vault, SQL Database, Cosmos DB, App Service, Container Registry and Event Hub. Only the sub-resource and the DNS zone name change. Because the test VM sits in the same VNet as the endpoint, no VNet peering is required.

What you need first

  • A VNet with a test VM already in it (I call it the development VNet below).
  • Permission to create a Storage Account, a subnet, a Private Endpoint and a Private DNS zone.
  • Azure CLI installed on the test VM.

Step 1: Create the Storage Account

  • In the portal, go to Storage accounts and select Create.
  • On Basics, choose the subscription, resource group, a globally unique account name, and a region that matches your VNet.
  • On Networking, set network access to Disable public access and use private access.
  • Select Review + Create, then Create.

Expected result: the account exists with all public network access disabled. At this point nobody can reach it, including you. That is intentional.

Step 2: Create a dedicated subnet for the Private Endpoint

  • Open the VNet, go to Subnets and select Subnet.
  • Name it something clear, such as subnet-privateendpoints.
  • Choose an unused address range inside the VNet, for example a /24.
  • Leave the other settings at their defaults and save.

Expected result: a new subnet, separate from the VM's subnet. Keeping endpoints in their own subnet makes NSG rules and later troubleshooting much simpler.

Step 3: Create the Private Endpoint

  • Open the Storage Account, go to Networking, then the Private endpoint connections tab.
  • Select Private endpoint.
  • On Basics, name it (for example pe-storage-blob) and match the VNet's region.
  • On Resource, set the target sub-resource to blob.
  • On Virtual Network, pick your VNet and the subnet-privateendpoints subnet.
  • On DNS, leave Integrate with private DNS zone set to Yes and accept the suggested zone, privatelink.blob.core.windows.net.
  • Select Review + Create, then Create.

Expected result: the endpoint is provisioned with a private IP inside the VNet, and the Private DNS zone is created and linked.

One endpoint serves one sub-resource. If you also need files, queues or tables, create a separate endpoint for each, each with its own privatelink zone.

Step 4: Verify the DNS configuration

DNS is where most Private Endpoint problems start, so check it before testing anything else.

  • Search for Private DNS zones and open privatelink.blob.core.windows.net.
  • Under Virtual network links, confirm your VNet is listed.
  • Under Recordsets, confirm an A record exists pointing to the endpoint's private IP.

Expected result: the zone is linked to the VNet and can resolve the storage account name to a private IP.

Step 5: Check NSG rules (if applicable)

  • Review any NSG attached to the VM's subnet and to the Private Endpoint's subnet.
  • Confirm traffic on port 443 is allowed between the two subnets.

Expected result: no NSG rule blocks port 443 between the VM subnet and the endpoint subnet.

If you have followed my earlier posts on NSG change detection, this is a good moment to confirm any rule change you make here shows up in Sentinel.

Step 6: Test DNS resolution from the VM

Connect to the test VM by RDP or SSH and run:

nslookup <storageaccount>.blob.core.windows.net

Expected result: the name resolves to a private IP address from your subnet range (for example 10.x.x.x), not a public Azure IP. This is the single most useful check in the whole guide.

Step 7: Test network connectivity from the VM

On Windows (PowerShell):

Test-NetConnection <storageaccount>.blob.core.windows.net -Port 443

On Linux:

nc -zv <storageaccount>.blob.core.windows.net 443

Expected result: the TCP connection on port 443 succeeds (TcpTestSucceeded : True, or "succeeded" on Linux).

Step 8: Test real data access from the VM

A successful port test does not prove you can read data. Test that too:

az login
az storage blob list --account-name <storageaccount> --container-name <container> --auth-mode login

Expected result: the blob list returns successfully, confirming the VM reaches the account privately.

Step 9: The negative control

A test is only convincing if you also show the failure case. From a device outside the VNet, such as a personal laptop or Azure Cloud Shell, repeat the request.

Do not use Test-NetConnection for this

It is tempting to repeat the port test from your laptop, but it can mislead you. The storage firewall works at the service layer, so the public endpoint can still accept a TCP connection on 443 and then reject the request. A successful port test from outside does not mean public access is open. Use a real data request instead:

# Should fail if public access is really disabled
Invoke-WebRequest -Uri "https://<storageaccount>.blob.core.windows.net/<container>/<blobname>"

Or with the Azure CLI:

az storage blob list --account-name <storageaccount> --container-name <container> --auth-mode login

If public access is correctly disabled, you should see an error such as:

This request is not authorized to perform this operation.

or a 403 or timeout. What you must not see is a successful blob list.

Expected result: the request fails, confirming the account cannot be reached over the public internet.

Troubleshooting

  • DNS still returns a public IP. Check the Private DNS zone is linked to the VNet and that the A record exists. Also check the VM is not using custom DNS servers that cannot forward to Azure DNS.
  • Port 443 is unreachable. Check NSG rules on both the VM subnet and the endpoint subnet, and check the effective routes on the VM's network interface.
  • Data access fails despite connectivity. This is usually permissions, not networking. Confirm the identity you used with az login has a data-plane RBAC role on the account, such as Storage Blob Data Reader or Storage Blob Data Contributor. Owner or Contributor on the account is not enough for --auth-mode login.

Takeaway

Creating the Private Endpoint is the quick part. The value comes from the checks that follow: DNS resolves privately, the port is reachable from inside, data can be read from inside, and the same request fails from outside. If all four hold, you have evidence the account is private, not just a setting that says so.

The same nine steps work for any other Private Link resource. Swap the sub-resource and the privatelink DNS zone and repeat the tests.
