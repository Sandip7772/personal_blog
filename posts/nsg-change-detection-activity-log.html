Detecting NSG changes in Microsoft Sentinel: what the Activity Log really gives you

A single Network Security Group (NSG) rule decides what traffic can reach your virtual machines. SSH or RDP opened to the whole internet is one of the most common causes of cloud compromise, and until recently we had no automated way to learn that a firewall rule had changed.

So I built a Sentinel detection for it. The query is the easy part. What took the time was understanding how the Azure Activity Log records an NSG change, because its behaviour is not what you would expect. This post covers those quirks, since they shape the whole design.

The goal was to answer three questions every time an NSG or one of its rules changes: what changed, who changed it, and how exposed the result is.

First, check the logs are arriving

Each subscription needs a subscription-level diagnostic setting sending the Administrative category to your Sentinel workspace. Before writing any detection, confirm every subscription you care about is actually reporting. Any subscription missing from this output is a blind spot:

AzureActivity
| where TimeGenerated > ago(7d)
| where OperationNameValue has "NETWORKSECURITYGROUPS"
| summarize Events = count(), Latest = max(TimeGenerated)
    by SubscriptionId, OperationNameValue

Quirk 1: one change produces three rows

Every NSG write emits three rows into AzureActivity, all sharing a CorrelationId:

  • Start carries the requestbody, the rule as submitted.
  • Accept carries the responseBody, the rule as accepted.
  • Success carries neither. It is confirmation only.

The row that proves a change applied and the row that says what changed are different rows. The query therefore joins them on CorrelationId: Success for confirmation, Start for the rule detail.

It also means an unfiltered query fires three times per change. Filtering the confirmation to Success is what prevents triplicate alerts.

Quirk 2: deletes carry no payload

A delete records only the resource path and the caller. There is no requestbody, so you can report that a rule was deleted, by whom and when, but not what it permitted.

My query handles deletes on a separate branch and fills the rule detail columns with n/a. This is a property of the Activity Log, not a gap in the query.

Quirk 3: Azure does not distinguish create from modify

Both are securityRules/write, because the underlying operation is a PUT. There is no create operation to filter on, so I infer the change type from the etag. An existing rule carries an etag when it is resubmitted, and a genuinely new rule has none to send:

| extend ChangeType = iff(isempty(Etag), "Created", "Modified")
Treat this as inference, not fact. Validate it in your own tenant: create a test rule, check the label, then edit it and confirm the label flips.

Quirk 4: editing a rule can report every rule

Editing a rule in the portal usually sends a PUT for the whole NSG, not the individual rule. The payload then contains every rule in that NSG, so expanding it outputs all of them as if each had changed. A twelve-rule NSG produces twelve rows for one edit.

The query handles both shapes by checking whether the payload holds a securityRules array:

| extend RuleSet = iff(isnotnull(Payload.properties.securityRules),
                       todynamic(Payload.properties.securityRules),
                       pack_array(Payload))
| mv-expand Rule = RuleSet

This over-reporting is still a known limitation. Comparing etags against the previous run would suppress the untouched rules, and I have not built that yet.

Grading the exposure

Once the rule detail is extracted, each change is graded so the dangerous ones stand out. An inbound Allow rule from Any, Internet or 0.0.0.0/0 is graded as follows:

  • Critical if the destination port is 22 or 3389, or any port.
  • High for any other internet-sourced inbound Allow.
  • Normal for everything else.

Because most NSG changes are routine, I run this rule at Low severity and use a separate High-severity rule, filtered to Critical and High exposure, for the ones that need action. Medium on the routine rule would bury real signals within a week.

What the Activity Log cannot tell you

This is the limitation that matters most. The Activity Log records change events, not current state. A permissive rule created before logging began, and never touched since, will never appear in it.

For current state you need Azure Resource Graph, which holds what every rule is right now. Sentinel analytics rules cannot query Resource Graph, so covering this gap needs another route, such as Defender for Cloud continuous export, a workbook, or a runbook that snapshots the results into a custom table. A change-based detection tells you what moved. It does not tell you what is already wrong.

Other limits worth knowing

  • Create vs modify is inferred from the etag, as above.
  • The MFA claim is not proof. I enrich each change with whether MFA was satisfied, but authnmethodsreferences reflects authentication at token issuance, and tokens refresh. A missing mfa is a reason to investigate, not a confirmed bypass.
  • Subscription names are not in the table. AzureActivity carries only the subscription ID, so you need a lookup. A Sentinel watchlist is the better long-term home for it.

Takeaway

The detection logic is short once you know the shape of the data. The real work was learning that one change means three rows, that deletes have no payload, that create and modify look identical, and that the log cannot see rules that already existed. Understanding those four things is what stops the rule from alerting three times, missing detail, or giving you false confidence.
