Tuning Sentinel analytics rules so they don't flood your queue

A detection query that returns the right rows is only half the job. The wrong scheduling or grouping settings can turn one firewall change into 144 duplicate incidents, or twelve changes into one alert that shows only one of them.

This post covers the settings I got wrong or nearly got wrong while building my NSG change rule in Microsoft Sentinel. The same lessons apply to most scheduled analytics rules.

Start disabled, and start at Low

Two choices on the first page of the rule wizard matter more than they look.

  • Severity: Low, not the Medium default. This rule fires on every NSG change, and most are routine. Medium would bury genuine signals within a week. Internet exposure is handled by a separate High-severity rule.
  • Status: Disabled at first. Check the expected alert volume on the later pages, then enable it. A rule that floods the queue overnight is hard to recover from with the team.

MITRE ATT&CK tagging is optional and only affects the coverage matrix. I used Defense Evasion with T1562.007 (Impair Defenses: Disable or Modify Cloud Firewall). If sub-techniques do not show, select the tactic alone.

The pairing rule: report must equal the run frequency

This is the single most important setting. The query has a report variable that sets how far back it looks. If it does not match how often the rule runs, one of two things happens:

  • Matched (hourly rule, report = 1h): each run examines the hour since the last run. Nothing is missed and nothing is seen twice.
  • Mismatched (hourly rule, report = 24h): every run re-examines the same 24 hours. A change at 09:00 alerts again on every run until it ages out. At a 10-minute frequency that is roughly 144 duplicate incidents for one change.

Why the lookup window is wider

The rule's own "lookup data from the last" window is set one hour wider than report. The query needs to reach the Start row, which carries the rule detail, even when its Success row lands near the edge of the window. Without the padding, a change at the boundary is reported with no rule detail.

  • Runs every 10 minutes: report = 10m, lookup window 20 minutes.
  • Runs every 1 hour: report = 1h, lookup window 2 hours.
  • Runs every 24 hours: report = 24h, lookup window 24 hours.

Set the scheduling fields before pasting the query, because the query's own ago() cannot reach further back than the lookup window. The field takes one number and one unit, so 1h 15m is not possible. Use 2 hours or 75 minutes.

Never change the frequency without changing report. The two must stay paired, or the rule duplicates or leaves gaps.

Event grouping: one alert per event

Set this to Trigger an alert for each event, not the default. The default collapses a run's results into a single alert, so the alert name and custom details resolve from one row. Twelve rule changes would then show one port, one source and one rule name, and most of the parsing work is lost.

I left the alert threshold at "is greater than 0" and suppression off.

Alert grouping: tame the incident queue

Event grouping and alert grouping are different layers, and mixing them up is common:

  • Event grouping controls how many alerts a run produces.
  • Alert grouping controls how many incidents those alerts become.

With one alert per event and alert grouping on, twelve changes by one person in an hour become twelve alerts inside one incident. Each alert keeps its own custom details, so no rule information is lost while the queue stays readable. My settings:

  • Group related alerts: Enabled, time frame 1 hour.
  • Grouping method: selected entity types and details match, with Account as the only entity.
  • Re-open closed matching incidents: Disabled.

Why Account and not "all entities match"

The recommended default sounds safer, but here it groups almost nothing. It requires the account, the IP and the Azure resource to all match, and every security rule has its own resource ID. A twelve-rule NSG save produces twelve distinct resources and therefore twelve separate incidents. Matching on Account alone gives one incident per person per hour, which is how the change would be investigated anyway.

Two more details

  • The grouping time frame should match the rule frequency. At 5 hours on an hourly rule, a change at 09:00 and an unrelated one at 13:00 land in the same ticket.
  • Leave re-open off. If it is on, a change tomorrow reopens yesterday's closed incident, which corrupts both the audit trail and your close-rate metrics.

For the High-severity exposure rule I do the opposite and disable alert grouping. Every internet-exposed rule should be its own incident with its own owner and closure note.

Alert enhancement: put the detail on the incident

Entity mapping

Entities let Sentinel correlate this incident with others involving the same person, IP or resource, and they drive the investigation graph. I map three:

  • Account (FullName) to AccountCustomEntity
  • IP (Address) to IPCustomEntity
  • Azure resource (ResourceId) to ResourceCustomEntity

These columns must survive the query's final project. If they are dropped, incidents are created with no entities and nothing warns you. A rule can also fail at runtime while its query runs fine in Logs, and a dropped column that entity mapping or a custom detail references is the usual cause.

Custom details and alert text

Custom details put the rule contents on the incident itself, so an analyst sees the port, source and action without opening Logs. I add each of these as a key and value pair using the same name for both: ChangeType, Exposure, Subscription, ResourceGroup, NSGName, RuleName, Priority, Direction, Action, Protocol, SourceIP, DestPort, DestinationIP, RoleUsed, PrincipalType and MfaSatisfied.

Use Subscription rather than SubscriptionName. The first carries the ID fallback for subscriptions missing from the lookup, and the second is blank for those.

The alert name and description formats use the same columns:

Name:        NSG {{ChangeType}}: {{NSGName}}/{{RuleName}} by {{DisplayName}}
Description: {{Action}} {{Direction}} {{Protocol}} port {{DestPort}} from {{SourceIP}}
             in {{Subscription}} - exposure {{Exposure}}. Caller {{Caller}}
             from {{CallerIpAddress}} using {{RoleUsed}}.

The description matters more than it looks, because the email playbook in the next post surfaces it as the "Detail" line. If it is blank, the notification arrives with no rule information at all.

Test before you enable

In the rule wizard, Test with current data replays the last 50 evaluations and projects alert volume. A flat line near zero with occasional spikes is what you want. Steady alerts every interval mean something matches constantly. Check the PrincipalType column first, since pipeline service principals are the usual cause.

If incidents are not being created at all, the health table shows why:

SentinelHealth
| where TimeGenerated > ago(1d)
| where SentinelResourceName has "NSG"
| project TimeGenerated, SentinelResourceName, Status, Description, ExtendedProperties
| order by TimeGenerated desc

Takeaways

  • Keep report equal to the run frequency, and pad the lookup window.
  • One alert per event, grouped into incidents by Account.
  • Routine changes at Low severity, with a separate High rule for exposure.
  • Keep the entity columns through the final project.
  • Start disabled, test with current data, then enable.
