Emailing Sentinel incidents with a Logic App playbook

A detection nobody sees does not protect anything. Once my NSG change rule was creating incidents, I wanted the right people to get an email with the key details and a link straight to the incident.

In Sentinel this takes three parts: a Logic App playbook that sends the email, a permission grant so Sentinel can run it, and an automation rule that triggers it. Most of the time went on the permissions and one account decision, so those get the most space here.

Part 1: the playbook

In Sentinel go to Automation, Create, Playbook with incident trigger. Pick a resource group and a region matching the workspace, and leave Log Analytics off.

On the Connections page only the Microsoft Sentinel connector appears. That is expected. This page pre-configures connectors Sentinel already knows the playbook needs, which at creation time is just the trigger's own. Leave it on Connect with managed identity. Outlook is added later, in the designer.

In the designer, add New step, Outlook, Send an email (V2). It prompts for sign-in at this point, and whoever authenticates becomes the sender.

Choose the sender carefully

The Office 365 connector authenticates as a user, and mail is sent from that account, including that user's Outlook signature. In my case the signature appended below the "do not reply" line.

That is cosmetic. The bigger problem is that this is a single point of failure. If that account is disabled, its password rotates or MFA re-prompts, the connection breaks and alerts stop silently. Nobody notices a notification that does not arrive.

Use a dedicated licensed service mailbox, not a personal account. You can switch later with Change connection in the designer, which takes a few clicks and not a rebuild.

Building the email body

There are two routes. The designer's Code preview is read-only, so writing HTML needs the Logic App's own code view (Logic App resource, Development Tools, Logic app code view). Or build the body from dynamic content in the designer, in which case two rules matter:

  • Type the labels. Chips inserted with no text between them produce values run together with no indication of what each one is.
  • Curly braces are not tokens. Typing {Incident Title} inserts literal characters. A real dynamic field renders as a coloured pill.

These field paths resolved correctly against a real incident payload:

triggerBody()?['object']?['properties']?['title']
triggerBody()?['object']?['properties']?['incidentNumber']
triggerBody()?['object']?['properties']?['severity']
triggerBody()?['object']?['properties']?['status']
triggerBody()?['object']?['properties']?['createdTimeUtc']
triggerBody()?['object']?['properties']?['description']
triggerBody()?['object']?['properties']?['incidentUrl']

Do not use additionalData.mergedIncidentNumber. It relates to incident merging and is null unless incidents have been merged. Use incidentNumber. The subject is simply [Sentinel] followed by the title.

The email itself is a small table with the incident number, severity, status and created time, then a Detail line from the incident description, and a button linking to the incident. That Detail line is why the alert description format in the previous post matters.

Permissions on the playbook

Grant the playbook's managed identity Microsoft Sentinel Responder on the workspace.

Part 2: letting Sentinel run the playbook

Without this step the playbook cannot be selected in an automation rule, and trying to run it by hand fails with:

Missing required permissions for Microsoft Sentinel on the playbook resource.

Sentinel's own service principal needs the Microsoft Sentinel Automation Contributor role on the resource group holding the Logic App. Go to Sentinel, Settings, Playbook permissions, Configure permissions, select the resource group and apply.

This action needs Owner or User Access Administrator on that resource group, because it assigns a role. Contributor is not enough. That is by design, so nobody can quietly escalate their own access.

Verify with the CLI, not the portal

The portal's Manage permissions screen caches, and can show "No permissions" for several minutes after a successful grant. Check the role assignment directly:

az role assignment list \
  --scope /subscriptions/<sub-id>/resourceGroups/<rg-name> \
  --query "[?roleDefinitionName=='Microsoft Sentinel Automation Contributor']" \
  -o table

A returned row with PrincipalType: ServicePrincipal confirms the grant, whatever the portal shows. RBAC propagation can take up to ten minutes, so hard-refresh the browser before assuming failure.

Part 3: the automation rule

Go to Sentinel, Automation, Create, Automation rule with these settings:

  • Trigger: When incident is created.
  • Condition: Analytic rule name contains NSG.
  • Action: Run playbook, then the playbook from part 1.
  • Rule expiration: indefinite.

In the playbook dropdown, two different greyed-out states look similar but mean different things:

  • A message about Microsoft Sentinel permissions means Sentinel lacks rights on that resource group. Grant them as above, or wait for propagation.
  • No user permissions means you lack rights on that Logic App, typically because it sits in a subscription you do not administer.

Do not email everything

This rule fires on every NSG change at Low severity, and that can get noisy. You can exclude Low severity so only the exposure rule emails, or reserve email for the exposure rule entirely and leave routine changes in the incident queue as an audit record. I prefer the second: email what needs action and review the rest in Sentinel.

Testing, fastest first

Method 1: run with a sample payload

This is the fastest route and needs no permission grant, because the Logic App triggers itself. In the designer use Run draft with payload. It expects a JSON incident payload, not HTML or the email body, and anything else returns "is not valid JSON". A minimal working payload:

{
  "object": {
    "properties": {
      "title": "NSG Deleted (rule): example-nsg by <user>",
      "incidentNumber": 3,
      "severity": "Low",
      "status": "New",
      "createdTimeUtc": "2026-09-23T10:44:56.961Z",
      "description": "n/a n/a n/a port n/a from n/a in Example subscription - exposure Review. Caller <user> from <ip> using Contributor.",
      "incidentUrl": "https://portal.azure.com"
    }
  }
}

For a payload that matches your tenant exactly, copy one from Run history, any previous run, the trigger, then Outputs.

Method 2: run against a real incident

Open an incident in Sentinel and choose Actions, Run playbook. This uses real data with no waiting, but needs the permission grant from part 2.

Method 3: end to end

Make a real change on a non-production NSG, then delete it, and wait for the scheduled run, the incident and the automation rule. It is the slowest but the only method that proves the whole chain. To avoid waiting an hour per cycle, temporarily set the rule to run every 5 minutes with a 20-minute lookup and report = 10m, then restore hourly afterwards.

In my test the n/a values in the email were correct, because my test change was a rule deletion and the Activity Log carries no payload for deletes.

When it does not work

Open the Logic App, then Run history, the run, then Send an email (V2) and its Inputs. This shows the body exactly as submitted, before sending. Blank values there point at the failing expression without waiting for mail to arrive. Click the trigger in the same run and read its Outputs to see the real payload structure, then correct the path to match.

If Detail is blank while the other fields populate, the Alert Description Format did not save on the analytics rule. Fix it there, not in the playbook.

Takeaways

  • Use a dedicated service mailbox as the sender. A personal account is a silent single point of failure.
  • Sentinel needs its own role on the playbook's resource group, and granting it needs Owner or User Access Administrator.
  • Trust the CLI over the portal when checking role assignments.
  • Email only what needs action, and keep routine changes in the queue.
  • Test with a sample payload first, then a real incident, then end to end.
